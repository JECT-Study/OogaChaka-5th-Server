# AI 셀프 리뷰 기준

PR 생성 전에 변경 코드가 팀 개발 컨벤션을 따르는지 검토한다.
아래 기준으로 컨벤션 위반, 중복, 예외 처리 및 로직 오류를 판단하고 P1~P5로 보고한다.

## 리뷰 수행 원칙

- 사용자가 지정한 diff·파일·커밋을 대상으로 관련 호출부, 설정, SQL까지 확인한다. 범위가 불명확하면 먼저 확인한다.
- 변경으로 발생한 문제를 중심으로 보고한다. 기존 문제를 언급할 때는 기존 문제임을 표시한다.
- 각 지적은 실제 코드 위치와 해당 기준에 근거한다. 발생 조건과 영향을 설명할 수 없는 추측을 결함으로 단정하지 않는다.
- 구현의 필요성은 실제 요구사항과 해결하려는 문제로 설명한다. **근거가 부족한 구현은 정리 대상이다.**
- 계층·분기·예외 처리·방어 로직을 추가하거나 유지할 때는 해당 코드가 없으면 어떤 문제가 발생하고, 현재 구현이 이를 어떻게 막는지 설명한다. "실무에서 흔히 사용한다" 또는 막연히 "보안을 위해서"라는 설명만으로 정당화하지 않는다.
- 설명이나 문서가 없다는 이유만으로 코드를 불필요하다고 단정하지 않는다. 실제 호출 흐름과 실패 조건을 확인해 근거를 보완하거나, 필요성을 확인할 수 없다면 제거·단순화를 검토한다.
- 문서의 권장 사항과 필수 규칙을 구분한다. 허용 예외나 팀에서 합의한 선택을 위반으로 처리하지 않는다.
- 규칙별로 억지로 지적을 만들지 않는다. 같은 원인은 하나로 묶고 문제가 없으면 발견 사항이 없다고 보고한다.
- 읽지 못한 코드, DB 적용 이력, 실행 결과는 확인 필요로 구분한다. 실행하지 않은 테스트를 통과했다고 표현하지 않는다.
- 코드 수정·테스트 실행·별도 결과 파일 생성은 요청받은 범위에서만 수행한다. 기본 결과는 대화로 제공한다.

## 우선순위와 결과 형식

| 우선순위 | 판단 기준 | 처리 기준 |
| --- | --- | --- |
| P1 | 반드시 수정할 심각한 오류: 보안 취약점, 데이터 손실, 핵심 기능 장애 등 | 해결 전 병합 불가 |
| P2 | 설계 결함, 성능 문제 등 중요한 개선 | 수정하거나 미반영 사유 공유 |
| P3 | 실제 팀 컨벤션 위반 또는 가독성 개선 | 수정 권장, 선택적 반영 |
| P4 | 사소한 개선, 취향에 가까운 제안 | 선택적 반영 |
| P5 | 개인 의견 및 참고 사항 | 반영 필수 아님 |

- 우선순위는 항목 이름이 아니라 실제 발생 조건과 영향으로 정한다.
- 컨벤션 위반은 보통 P3지만, 데이터 손실·보안 문제로 이어진다면 그 영향에 맞게 P1/P2로 판단한다.
- 단순 취향 차이는 P4~P5로 분류한다. AI가 부여한 우선순위는 개발자가 조정할 수 있다.
- 모든 리뷰 의견은 `Pn: 문제 요약`으로 시작하고 높은 우선순위부터 제시한다.

```text
P3: 엔티티 생성 메서드가 API 요청 DTO에 직접 의존합니다.
- 위치: src/main/java/.../User.java:32
- 기준: 3. DTO ↔ Entity 변환 — Entity는 API DTO에 의존하지 않는다.
- 원인·영향: create(UserCreateRequest)가 요청 형식과 엔티티 생성을 결합해 API 변경이 엔티티에 전파됩니다.
- 개선 방향: Service에서 필요한 값을 꺼내 create(...)에 전달하세요.
```

마지막에 검토 범위와 확인하지 못한 사항만 짧게 덧붙인다.

## 1. 패키지 구조

**검토·판단 기준**

- 최상위 업무 패키지가 도메인 단위로 나뉘고, 하위 controller·dto·entity·repository·service의 책임에 맞게 코드가 배치되는지 확인한다.
- 여러 도메인에서 사용하는 공통 기능이 global에 있는지, 특정 도메인 로직이 공통 코드에 섞이지 않았는지 확인한다.
- ErrorCode와 SuccessCode는 global.response.code, 공통 응답은 global.response, 비즈니스 예외와 처리기는 global.exception에서 관리하는지 확인한다.
- 실제 구현 없이 repository/impl 등 불필요한 계층을 만드는지 확인한다.

**허용 예외**

- 예시 도메인이나 사용하지 않는 하위 패키지가 없다는 이유로 위반을 지적하지 않는다. 실제 역할과 사용 여부로 판단한다.

## 2. Java 네이밍

**검토·판단 기준**

- 클래스는 역할이 드러나는 PascalCase 명사·명사구, 메서드는 동사로 시작하는 camelCase인지 확인한다.
- 변수는 의미 있는 camelCase, 패키지는 소문자, 상수는 static final 및 UPPER_SNAKE_CASE인지 확인한다.
- 불명확한 축약과 클래스명으로 이미 드러난 대상의 불필요한 반복을 확인한다.
- DTO에 Request/Response 접미사가 있고 필요하면 Create·Update·Register 등 목적이 드러나는지 확인한다.
- create는 생성, get/getById는 없으면 예외가 발생하는 필수 단건 조회, find/findById는 Optional을 활용하는 선택 조회인지 확인한다.
- list·update·delete가 각각 다건 조회·수정·삭제의 의미와 일치하는지 확인한다.
- 단일 리소스 Path Variable은 {id}, 여러 리소스 ID가 포함된 URL은 {familyId}·{userId}처럼 구분하는지 확인한다.

**허용 예외**

- approve·reject·deactivate 등 비즈니스 의미가 분명한 메서드명을 허용한다.
- @Slf4j가 제공하는 log는 상수 이름 규칙의 예외다.
- 프레임워크가 제공하거나 요구하는 메서드 이름을 팀 명명 규칙에 맞추려고 변경하도록 요구하지 않는다.
- 테스트 메서드명에는 한글을 허용한다. 테스트 목적을 설명하는 주석 기준은 11번을 따른다.

## 3. DTO ↔ Entity 변환

**검토·판단 기준**

- Entity가 API Request/Response DTO를 매개변수·필드 등으로 직접 참조하는지 확인한다.
- Service가 Request에서 필요한 값을 꺼내 Entity.create(...)에 전달하는지 확인한다.
- 생성 과정에서 필요한 기본값, 필수 값, 비즈니스 규칙이 빠지지 않았는지 확인한다.
- 여러 값 조합에는 of(...), 다른 객체의 변환에는 from(...)을 사용하는지 확인한다.
- Entity → Response 변환이 Response.from(entity)에 모여 있고 같은 변환이 중복되는지 확인한다.

**허용 예외**

- 인자가 많고 생성이 단순하면 Builder 사용을 허용한다. Builder 자체를 위반으로 지적하지 않는다.
- 복잡한 생성 규칙을 위해 동일 도메인 계층의 생성 객체를 받는 것은 API DTO 의존과 구분한다.
- 인자가 많다는 이유만으로 별도 생성 객체를 만들도록 요구하지 않는다.

## 4. 사용자 정의 예외

**검토·판단 기준**

- 비즈니스 실패를 BusinessException과 ErrorCode로 표현하고, ErrorCode에서 HTTP 상태를 관리하는지 확인한다.
- @RestControllerAdvice가 해당 상태와 공통 오류 응답을 반환하는지 확인한다.
- 필수 단건 조회 실패, 잘못된 상태 등 업무상 실패를 누락하거나 예외를 삼켜 성공으로 반환하는지 확인한다.
- 동일한 의미의 오류 코드나 상태 차이만을 위한 예외 클래스가 불필요하게 늘어나는지 확인한다.

**허용 예외**

- 기본은 단일 BusinessException이지만 별도 처리 책임이 있으면 예외 클래스를 확장할 수 있다.
- 암호화·복호화 오류는 10번 기준에 따라 별도 예외로 관리한다. 이를 단일 예외 원칙 위반으로 지적하지 않는다.
- 인증 필터 등 Advice를 거치지 않는 실패는 실제 처리 경계를 확인한 뒤 판단한다.

## 5. 공통 API 응답

**검토·판단 기준**

- 일반 JSON API가 ApiResponse<T>의 code·message·data 구조를 사용하는지 확인한다.
- 성공은 SuccessCode, 실패는 ErrorCode를 사용하며, 데이터가 없으면 data가 null인지 확인한다.
- HTTP 상태와 비즈니스 응답 코드를 혼동하지 않는지 확인한다. 본문에 CREATED를 넣는 것만으로 HTTP 201이 설정되지는 않는다.
- 실패 응답이 원칙적으로 Advice에서 생성되고 ErrorCode에 맞는 HTTP 상태를 반환하는지 확인한다.

**허용 예외**

- 파일 다운로드와 본문 없는 204 응답에 ApiResponse를 강제하지 않는다.
- 상황에 맞는 사용자 정의 오류 메시지는 허용한다.

## 6. 트랜잭션

**검토·판단 기준**

- DB 트랜잭션을 사용하는 Service 클래스에는 @Transactional(readOnly = true)를 기본으로 선언한다. 메서드별 선언만으로 클래스 기본 선언을 생략하지 않는다.
- 생성·수정·삭제 및 조회 중 생성이 가능한 메서드는 메서드에 @Transactional을 선언해 쓰기 트랜잭션으로 재정의한다. MANDATORY·REQUIRES_NEW 등 업무상 필요한 전파 설정은 유지한다.
- 조회 메서드에 전파 설정 등을 위해 @Transactional을 별도로 선언할 때는 readOnly = true도 명시한다. 메서드의 어노테이션은 클래스 설정을 대체하므로 클래스의 readOnly 값이 자동으로 합쳐진다고 가정하지 않는다.
- 함께 성공·실패해야 하는 작업이 분리되어 부분 반영되거나, 호출 방식 때문에 의도한 트랜잭션이 적용되지 않는지 확인한다.

**허용 예외**

- DB 트랜잭션이 필요 없는 외부 API·Redis 조정 서비스와 암호화·해시 등 계산 전용 서비스에는 클래스 기본 선언을 강제하지 않는다. 해당 작업을 감싸기 위해 DB 트랜잭션을 새로 열지 않는다.
- 외부 API 호출과 별도 트랜잭션 경계는 업무 흐름에 따라 설계할 수 있다.

## 7. 도메인 간 의존성

**검토·판단 기준**

- 각 Service가 자기 도메인의 Repository(Mapper)에 접근하고, 다른 도메인 기능은 그 도메인의 Service를 사용하는지 확인한다.
- 다른 도메인의 Repository를 직접 호출하여 해당 도메인의 검증·비즈니스 규칙을 우회하는지 확인한다.
- Service 간 순환 의존이 생기는지 확인하고, 필요하면 책임 분리나 조정 Service를 제안한다.

**허용 예외**

- 복잡한 데이터 조합 조회나 Service 호출이 비효율적인 경우 팀 합의로 QueryService·조회 전용 Repository 등을 사용할 수 있다.
- 합의 여부가 불명확하면 확인 필요로 남긴다. 무조건 계층을 추가하도록 요구하지 않는다.

## 8. DB 스키마와 Flyway

**검토·판단 기준**

- ddl-auto가 validate이고, 테이블 생성·변경이 SQL 마이그레이션으로 관리되는지 확인한다.
- 파일이 src/main/resources/db/migration/에 있고 V{버전}__{변경내용}.sql 형식인지 확인한다.
- 대문자 V, 순차 증가하는 버전, 이중 언더스코어, 영문 소문자·언더스코어로 된 변경 설명 및 버전 충돌을 확인한다.
- 엔티티 변경에 필요한 SQL이 있고 타입·길이·null 허용·제약조건이 일치하는지 확인한다.
- 공용 테스트 DB에 적용된 파일을 수정·삭제하지 않고 새 버전을 추가하는지 확인한다.
- 배포 설정을 확인할 수 있다면 공용 DB에 팀 공용 개발 브랜치에 병합된 마이그레이션만 적용되는지 확인한다.
- 공용 DB에 직접 ALTER TABLE 등을 실행하거나 로컬 실험용 변경을 반영하려는 절차가 있는지 확인한다.

**허용 예외·확인 한계**

- 초기 스키마 확정 전 로컬 실험과 공용 DB에 이미 반영된 마이그레이션을 구분한다.
- 확정된 초기 스키마는 V1, 이후 변경은 새 버전으로 관리한다. 미확정 설계에 빈 V1을 요구하지 않는다.
- 적용 이력을 보지 못했다면 기존 파일이 이미 적용되었다고 단정하지 말고 확인을 요청한다.

## 9. ENUM

**검토·판단 기준**

- 정해진 상태·역할·유형에 사용하며 타입은 PascalCase, 상수는 UPPER_SNAKE_CASE인지 확인한다.
- 영속 필드가 @Enumerated(EnumType.STRING)을 사용하고 ORDINAL을 사용하지 않는지 확인한다.
- DB 컬럼은 기본 VARCHAR이며 실제 ORM 매핑과 SQL의 타입·길이가 일치하는지 확인한다. MySQL/Hibernate에서는 @JdbcTypeCode(SqlTypes.VARCHAR) 같은 명시적 매핑을 확인한다.
- 상수 추가 시 관련 분기가 누락되지 않았는지, 이름 변경·삭제 시 기존 DB 값과 API 소비자에 대한 영향을 검토했는지 확인한다.
- 데이터 변경이 필요하면 Flyway 마이그레이션이 있는지 확인한다.
- 도메인 전용은 해당 도메인.enums, 실제 공유 타입만 global.enums에 배치하는지 확인한다.

**허용 예외**

- ErrorCode와 SuccessCode는 global.response.code에 함께 둔다.
- 이름 변경·삭제 자체를 무조건 금지하지 않는다. 영향 검토와 필요한 데이터 전환이 준비됐는지 판단한다.

## 10. 암호화 및 민감정보

### 10.1. 기본 원칙과 대상 데이터

- 민감도·저장 필요성·조회 목적을 기준으로 AES, HMAC, 평문을 구분했는지 확인한다.
- 복원이 필요하면 AES-256-GCM, 식별·중복 검사만 필요하면 HMAC-SHA256을 사용하는지 확인한다.
- 비밀번호를 저장한다면 BCrypt·Argon2id 같은 비밀번호 전용 해시를 사용하는지 확인한다.
- 소셜 사용자 ID는 HMAC만 저장하고 원문을 별도 컬럼이나 로그에 남기지 않는지 확인한다.
- FCM 디바이스 토큰은 AES로 저장하고 발송 시 복호화하며, 중복 검사는 별도 token_hash로 수행하는지 확인한다.
- 이메일은 MVP에서 평문 저장을 허용하되 로그·응답 노출을 제한하는지 확인한다. 일반 ID·역할·포인트에 불필요한 암호화를 강제하지 않는다.
- 주민등록번호 등 새 민감정보는 수집 필요성·근거부터 검토하고 필요한 경우에만 저장하는지 확인한다.

### 10.2. AES 암호화 구현

- EncryptionService·EncryptionConverter·HmacService·EncryptionException이 global.crypto에, 키 설정이 global.config에 있는지 확인한다.
- 알고리즘이 공통 서비스에 모여 있고 도메인별 중복 구현이 없는지 확인한다.
- AES-256-GCM의 32바이트 키, 12바이트 IV, 128비트 태그를 사용하는지 확인한다.
- 매 암호화마다 SecureRandom으로 새 IV를 생성하고, 고정 IV·동일 키의 IV 재사용·태그 검증 누락이 없는지 확인한다.
- 버전:Base64(IV + 암호문 + 태그) 형식과 버전별 키 선택으로 기존 데이터 복호화를 지원하는지 확인한다.
- Base64 인코딩만 수행한 값을 암호화로 간주하지 않는지 확인한다.

### 10.3. HMAC 구현과 입력 규칙

- HmacService가 HmacSHA256 결과를 소문자 hex 64자리로 생성하는지 확인한다.
- AES 키와 HMAC 키, 소셜 ID용과 디바이스 토큰용 HMAC 키가 각각 분리되는지 확인한다.
- 소셜 로그인·회원가입의 서비스 계층에서 명시적으로 HMAC을 생성하며 AttributeConverter로 해시하지 않는지 확인한다.
- 조회와 저장에 동일한 원본 입력·정규화 규칙·용도별 키를 사용하고, 이미 해시된 값을 다시 해시하지 않는지 확인한다.
- 현재 공통 API는 원본 UTF-8 문자열을 사용하며 trim·대소문자 변경·Unicode 정규화를 하지 않는다. 도메인이 임의로 다른 규칙을 적용하지 않는지 확인한다.

### 10.4. JPA 변환

- EncryptionConverter가 AttributeConverter<String, String>을 구현하고 실제 처리를 EncryptionService에 위임하는지 확인한다.
- @Converter(autoApply = false)와 필드의 명시적 @Convert로 대상을 제한하는지 확인한다.
- Hibernate의 Spring bean container 연동으로 Converter의 생성자 주입이 가능한지 확인한다.
- null을 그대로 처리하며 Service에서 중복 암호화·복호화하지 않는지 확인한다.
- Native Query·JDBC 등 Converter를 우회하는 경로에서 자동 변환을 가정하지 않는지 확인한다.
- 로딩 시 복호화되는 엔티티의 접근 권한과 API 응답 범위를 확인한다.

### 10.5. 키 관리와 교체

- 키를 Java 코드·DB에 직접 저장하거나 실제 키가 든 .env·설정 파일을 커밋하지 않는지 확인한다.
- AES·HMAC·JWT 서명 키는 환경변수로 주입하고, DB 접속 정보·OAuth secret은 Jasypt ENC(...)로 보호하는지 확인한다.
- 로컬·테스트·운영 키를 분리하고 누락·Base64 오류·키 길이 오류·AES/HMAC 키 재사용 시 시작 단계에서 실패하는지 확인한다.
- AES 교체 후 이전 키로 복호화하거나 재암호화할 수 있는지, 키 분실·백업 복구의 영향을 고려했는지 확인한다.
- HMAC 키 변경 시 기존 소셜 계정 식별이 끊길 수 있음을 인지하고 데이터 전환·계정 재연동 절차를 준비했는지 확인한다.
- 디바이스 토큰 HMAC 키 변경 시 token_hash 백필과 전환 중 중복 검사 일관성을 고려했는지 확인한다.

**허용 예외·확인 한계**

- 초기 환경의 환경변수 주입을 허용한다. 운영은 KMS·Secrets Manager를 우선 검토하되 특정 서비스를 강제하지 않는다.
- 명시적 테스트 더미 키는 허용한다. 운영 키 보관 권한·백업 등 코드에서 알 수 없는 사항은 확인 필요로 남긴다.

### 10.6. 검색과 UNIQUE KEY

- 무작위 IV를 쓰는 AES 컬럼을 원본 기준 동등 비교·LIKE·중복 검사에 사용하지 않는지 확인한다.
- 검색용 Blind Index가 필요하면 별도 HMAC 컬럼을 사용하고 평문 복사본이나 전체 복호화 비교로 우회하지 않는지 확인한다.
- provider_user_id_hash와 token_hash가 CHAR(64) CHARACTER SET ascii COLLATE ascii_bin NOT NULL인지 확인한다.
- 소셜 계정은 (auth_provider, provider_user_id_hash) 복합 UNIQUE로 조회·중복을 검사하는지 확인한다.
- 사용자당 한 소셜 계정 정책의 uk_social_account_user(user_id)를 유지하고, 디바이스 token_hash는 전역 UNIQUE인지 확인한다.

### 10.7. DB 변경과 저장 크기

- 원문의 최대 바이트 길이에 IV·태그·버전·Base64 증가분을 더해 실제 컬럼 용량을 산정했는지 확인한다.
- 암호문에는 필요에 따라 TEXT·VARBINARY를 허용하고 HMAC hex에는 CHAR(64)를 사용하는지 확인한다.
- 컬럼 변경은 새 Flyway로 관리하고 기존 평문·다른 해시·키 변경 데이터의 전환 절차가 있는지 확인한다.
- 기존 행에 NOT NULL·UNIQUE를 추가할 때 백필·중복 정리와 적용 실패 가능성을 검토했는지 확인한다.

### 10.8. 실패 처리와 정보 노출

- 암호화 실패 시 평문 저장, 복호화 실패 시 기본값·암호문 반환으로 대체하지 않는지 확인한다.
- 암호화·복호화·HMAC 오류를 공통 예외로 관리하고 공통 오류 응답/실패 상태로 연결하는지 확인한다.
- 키·원문·인증 토큰이 로그·공급자 예외 메시지·API 응답에 노출되지 않는지 확인한다.
- 오류 로그에는 민감정보를 제외한 유형과 필요한 추적 식별자만 남기는지 확인한다.
- 복호화된 응답은 사용자 권한을 검증하고 필요한 필드만 반환하는지 확인한다.

**허용 예외**

- 암호화 오류는 업무 실패와 구분되는 공통 예외를 허용한다. 시작 시 설정 검증 실패는 요청용 BusinessException으로 변환하지 않는다.

### 10.9. 테스트 존재 및 범위

암호화 기능이 변경되면 다음 위험 중 해당 변경과 관련된 항목을 검증하는지 확인한다.
매번 모든 항목을 새로 작성하거나 여러 계층에서 반복 검증하도록 요구하지 않는다. 테스트의 필요성과 설명은 11번 기준을 함께 따른다.

- AES 왕복 일치, 반복 암호화 시 서로 다른 암호문/IV, 암호문·태그 변조 및 잘못된 키의 복호화 실패
- null 처리, 버전별 키 교체, JPA 저장·조회 자동 변환 및 실제 암호문의 컬럼 용량 준수
- HMAC의 동일 키/입력 결정성, 다른 입력/키/용도에 따른 결과 차이와 hex 64자리 형식
- 생성한 해시로 기존 소셜 계정 조회, 동일 제공자/ID의 UNIQUE 중복 차단, 다른 제공자의 같은 ID 구분
- 키 설정의 시작 시 검증 및 오류 메시지의 민감정보 비노출

테스트 작성 여부와 실제 실행 결과를 구분한다. 리뷰만 요청받았다면 임의로 실행하지 않고 확인한 범위만 보고한다.

## 11. 테스트의 필요성과 설명

**검토·판단 기준**

- 테스트마다 어떤 오류나 회귀를 잡기 위해 남기는지 설명할 수 있어야 한다. 테스트가 있다는 이유만으로 해당 동작이 특별히 중요한 요구사항인 것처럼 보이지 않도록 한다.
- 모든 테스트 메서드의 어노테이션 바로 위에 한국어 주석을 남긴다. 어떤 입력·상황에서 무엇을 기대하는지 코드 본문을 해석하지 않아도 알 수 있게 작성한다.
- 메서드명은 한글 또는 의미가 분명한 영어를 사용한다. 이름이 모호하면 주석만 덧붙이지 말고 실제 검증 범위에 맞게 고친다.
- 주석은 "정상 동작 확인", "조회 테스트"처럼 포괄적으로 쓰지 않는다. 예를 들어 "Redis가 refresh 교체를 거부하면 새 토큰을 응답하지 않고 AUTH_TOKEN_INVALID로 중단한다"처럼 조건과 결과를 명시한다.
- 테스트 클래스에는 검증 대상과 경계를 설명한다. 목 객체로 대체한 DB·Redis·외부 API를 실제로 검증한 것처럼 이름이나 주석에 표현하지 않는다.
- 실제 Redis의 원자성, DB 트랜잭션 롤백, 소셜 제공자 연동은 해당 경계를 실행해야 검증할 수 있다. 목 객체의 반환값이나 예외를 지정한 테스트는 호출자의 대응만 확인한다고 설명한다.
- 단순 getter, DTO 값 전달, 목 객체에 지정한 값의 재확인, 의미 없는 호출 횟수, 프레임워크의 기본 저장·조회 동작만 확인하는 테스트는 기본적으로 추가하지 않고 기존 테스트에서도 제거를 검토한다.
- 같은 동작을 여러 계층에서 반복 검증하지 않는다. JWT 자체의 서명·만료는 토큰 검증 테스트에서, HTTP 인증 경계·상태·응답 계약은 MVC 테스트에서 확인하는 식으로 적절한 경계를 선택한다.
- 보안 우회, 토큰 재사용, 데이터 불일치, 롤백 실패, 실제 응답 계약의 회귀를 잡는 검증에 집중한다. 테스트 실행 횟수나 커버리지 숫자를 늘리기 위한 테스트는 추가하지 않는다.
- 매개변수 반복 실행은 서로 다른 실패 조건이나 경계를 확인할 때 사용한다. 값만 다르고 검증 의미가 같다면 줄인다.
- 테스트를 수정할 때는 주석도 실제 검증 내용과 일치하는지 확인한다. 주석만으로 목적을 설명할 수 없다면 테스트의 필요성과 범위를 먼저 다시 검토한다.

**실행 환경**

- `test`는 Docker와 외부 서버 없이 실행 가능한 단위·MVC 테스트만 유지한다.
