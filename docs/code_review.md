# AI 셀프 리뷰 기준

PR 생성 전에 변경 코드가 팀 개발 컨벤션을 따르는지 검토한다.
아래 기준으로 컨벤션 위반, 중복, 예외 처리 및 로직 오류를 판단하고 P1~P5로 보고한다.

## 리뷰 수행 원칙

- 사용자가 지정한 diff·파일·커밋을 대상으로 관련 호출부, 설정, SQL까지 확인한다. 범위가 불명확하면 먼저 확인한다.
- 변경으로 발생한 문제를 중심으로 보고한다. 기존 문제를 언급할 때는 기존 문제임을 표시한다.
- 각 지적은 실제 코드 위치와 해당 기준에 근거한다. 발생 조건과 영향을 설명할 수 없는 추측을 결함으로 단정하지 않는다.
- 문서의 권장 사항과 필수 규칙을 구분한다. 허용 예외나 팀에서 합의한 선택을 위반으로 처리하지 않는다.
- 규칙별로 억지로 지적을 만들지 않는다. 같은 원인은 하나로 묶고 문제가 없으면 발견 사항이 없다고 보고한다.
- 읽지 못한 코드, DB 적용 이력, 실행 결과는 확인 필요로 구분한다. 실행하지 않은 테스트를 통과했다고 표현하지 않는다.
- 코드 수정·테스트 실행·별도 결과 파일 생성은 요청받은 범위에서만 수행한다. 기본 결과는 대화로 제공한다.

## 우선순위와 결과 형식

| 우선순위 | 판단 기준 | 처리 기준 |
| --- | --- | --- |
| P1 | 반드시 수정할 심각한 오류: 보안 취약점, 데이터 손실, 핵심 기능 장애 등 | 해결 전 병합 불가 |
| P2 | 설계 결함, 성능 문제 등 중요한 개선 | 수정하거나 미반영 사유 공유 |
| P3 | 실제 팀 컨벤션 위반 또는 가독성 개선 | 수정 권장, 선택적 반영 |
| P4 | 사소한 개선, 취향에 가까운 제안 | 선택적 반영 |
| P5 | 개인 의견 및 참고 사항 | 반영 필수 아님 |

- 우선순위는 항목 이름이 아니라 실제 발생 조건과 영향으로 정한다.
- 컨벤션 위반은 보통 P3지만, 데이터 손실·보안 문제로 이어진다면 그 영향에 맞게 P1/P2로 판단한다.
- 단순 취향 차이는 P4~P5로 분류한다. AI가 부여한 우선순위는 개발자가 조정할 수 있다.
- 모든 리뷰 의견은 `Pn: 문제 요약`으로 시작하고 높은 우선순위부터 제시한다.

```text
P3: 엔티티 생성 메서드가 API 요청 DTO에 직접 의존합니다.
- 위치: src/main/java/.../User.java:32
- 기준: 3. DTO ↔ Entity 변환 — Entity는 API DTO에 의존하지 않는다.
- 원인·영향: create(UserCreateRequest)가 요청 형식과 엔티티 생성을 결합해 API 변경이 엔티티에 전파됩니다.
- 개선 방향: Service에서 필요한 값을 꺼내 create(...)에 전달하세요.
```

마지막에 검토 범위와 확인하지 못한 사항만 짧게 덧붙인다.

## 1. 패키지 구조

**검토·판단 기준**

- 최상위 업무 패키지가 도메인 단위로 나뉘고, 하위 controller·dto·entity·repository·service의 책임에 맞게 코드가 배치되는지 확인한다.
- 여러 도메인에서 사용하는 공통 기능이 global에 있는지, 특정 도메인 로직이 공통 코드에 섞이지 않았는지 확인한다.
- ErrorCode와 SuccessCode는 global.response.code, 공통 응답은 global.response, 비즈니스 예외와 처리기는 global.exception에서 관리하는지 확인한다.
- 실제 구현 없이 repository/impl 등 불필요한 계층을 만드는지 확인한다.

**허용 예외**

- 예시 도메인이나 사용하지 않는 하위 패키지가 없다는 이유로 위반을 지적하지 않는다. 실제 역할과 사용 여부로 판단한다.

## 2. Java 네이밍

**검토·판단 기준**

- 클래스는 역할이 드러나는 PascalCase 명사·명사구, 메서드는 동사로 시작하는 camelCase인지 확인한다.
- 변수는 의미 있는 camelCase, 패키지는 소문자, 상수는 static final 및 UPPER_SNAKE_CASE인지 확인한다.
- 불명확한 축약과 클래스명으로 이미 드러난 대상의 불필요한 반복을 확인한다.
- DTO에 Request/Response 접미사가 있고 필요하면 Create·Update·Register 등 목적이 드러나는지 확인한다.
- create는 생성, get/getById는 없으면 예외가 발생하는 필수 단건 조회, find/findById는 Optional을 활용하는 선택 조회인지 확인한다.
- list·update·delete가 각각 다건 조회·수정·삭제의 의미와 일치하는지 확인한다.
- 단일 리소스 Path Variable은 {id}, 여러 리소스 ID가 포함된 URL은 {familyId}·{userId}처럼 구분하는지 확인한다.

**허용 예외**

- approve·reject·deactivate 등 비즈니스 의미가 분명한 메서드명을 허용한다.
- @Slf4j가 제공하는 log는 상수 이름 규칙의 예외다.
- 프레임워크가 제공하거나 요구하는 메서드 이름을 팀 명명 규칙에 맞추려고 변경하도록 요구하지 않는다.

## 3. DTO ↔ Entity 변환

**검토·판단 기준**

- Entity가 API Request/Response DTO를 매개변수·필드 등으로 직접 참조하는지 확인한다.
- Service가 Request에서 필요한 값을 꺼내 Entity.create(...)에 전달하는지 확인한다.
- 생성 과정에서 필요한 기본값, 필수 값, 비즈니스 규칙이 빠지지 않았는지 확인한다.
- 여러 값 조합에는 of(...), 다른 객체의 변환에는 from(...)을 사용하는지 확인한다.
- Entity → Response 변환이 Response.from(entity)에 모여 있고 같은 변환이 중복되는지 확인한다.

**허용 예외**

- 인자가 많고 생성이 단순하면 Builder 사용을 허용한다. Builder 자체를 위반으로 지적하지 않는다.
- 복잡한 생성 규칙을 위해 동일 도메인 계층의 생성 객체를 받는 것은 API DTO 의존과 구분한다.
- 인자가 많다는 이유만으로 별도 생성 객체를 만들도록 요구하지 않는다.

## 4. 사용자 정의 예외

**검토·판단 기준**

- 비즈니스 실패를 BusinessException과 ErrorCode로 표현하고, ErrorCode에서 HTTP 상태를 관리하는지 확인한다.
- @RestControllerAdvice가 해당 상태와 공통 오류 응답을 반환하는지 확인한다.
- 필수 단건 조회 실패, 잘못된 상태 등 업무상 실패를 누락하거나 예외를 삼켜 성공으로 반환하는지 확인한다.
- 동일한 의미의 오류 코드나 상태 차이만을 위한 예외 클래스가 불필요하게 늘어나는지 확인한다.

**허용 예외**

- 기본은 단일 BusinessException이지만 별도 처리 책임이 있으면 예외 클래스를 확장할 수 있다.
- 암호화·복호화 오류는 10번 기준에 따라 별도 예외로 관리한다. 이를 단일 예외 원칙 위반으로 지적하지 않는다.
- 인증 필터 등 Advice를 거치지 않는 실패는 실제 처리 경계를 확인한 뒤 판단한다.

## 5. 공통 API 응답

**검토·판단 기준**

- 일반 JSON API가 ApiResponse<T>의 code·message·data 구조를 사용하는지 확인한다.
- 성공은 SuccessCode, 실패는 ErrorCode를 사용하며, 데이터가 없으면 data가 null인지 확인한다.
- HTTP 상태와 비즈니스 응답 코드를 혼동하지 않는지 확인한다. 본문에 CREATED를 넣는 것만으로 HTTP 201이 설정되지는 않는다.
- 실패 응답이 원칙적으로 Advice에서 생성되고 ErrorCode에 맞는 HTTP 상태를 반환하는지 확인한다.

**허용 예외**

- 파일 다운로드와 본문 없는 204 응답에 ApiResponse를 강제하지 않는다.
- 상황에 맞는 사용자 정의 오류 메시지는 허용한다.

## 6. 트랜잭션

**검토·판단 기준**

- 기본 트랜잭션 경계가 Service에 있고 조회는 readOnly = true, 생성·수정·삭제는 쓰기 트랜잭션인지 확인한다.
- 클래스에 readOnly = true가 있을 때 쓰기 메서드가 @Transactional로 재정의되는지 확인한다.
- 함께 성공·실패해야 하는 작업이 분리되어 부분 반영되거나, 호출 방식 때문에 의도한 트랜잭션이 적용되지 않는지 확인한다.

**허용 예외**

- 클래스에 조회 전용을 선언하는 것은 권장 방식이다. 메서드별 선언도 실제 동작이 맞으면 허용한다.
- 외부 API 호출과 별도 트랜잭션 경계는 업무 흐름에 따라 설계할 수 있다.

## 7. 도메인 간 의존성

**검토·판단 기준**

- 각 Service가 자기 도메인의 Repository(Mapper)에 접근하고, 다른 도메인 기능은 그 도메인의 Service를 사용하는지 확인한다.
- 다른 도메인의 Repository를 직접 호출하여 해당 도메인의 검증·비즈니스 규칙을 우회하는지 확인한다.
- Service 간 순환 의존이 생기는지 확인하고, 필요하면 책임 분리나 조정 Service를 제안한다.

**허용 예외**

- 복잡한 데이터 조합 조회나 Service 호출이 비효율적인 경우 팀 합의로 QueryService·조회 전용 Repository 등을 사용할 수 있다.
- 합의 여부가 불명확하면 확인 필요로 남긴다. 무조건 계층을 추가하도록 요구하지 않는다.

## 8. DB 스키마와 Flyway

**검토·판단 기준**

- ddl-auto가 validate이고, 테이블 생성·변경이 SQL 마이그레이션으로 관리되는지 확인한다.
- 파일이 src/main/resources/db/migration/에 있고 V{버전}__{변경내용}.sql 형식인지 확인한다.
- 대문자 V, 순차 증가하는 버전, 이중 언더스코어, 영문 소문자·언더스코어로 된 변경 설명 및 버전 충돌을 확인한다.
- 엔티티 변경에 필요한 SQL이 있고 타입·길이·null 허용·제약조건이 일치하는지 확인한다.
- 공용 테스트 DB에 적용된 파일을 수정·삭제하지 않고 새 버전을 추가하는지 확인한다.
- 배포 설정을 확인할 수 있다면 공용 DB에 팀 공용 개발 브랜치에 병합된 마이그레이션만 적용되는지 확인한다.
- 공용 DB에 직접 ALTER TABLE 등을 실행하거나 로컬 실험용 변경을 반영하려는 절차가 있는지 확인한다.

**허용 예외·확인 한계**

- 초기 스키마 확정 전 로컬 실험과 공용 DB에 이미 반영된 마이그레이션을 구분한다.
- 확정된 초기 스키마는 V1, 이후 변경은 새 버전으로 관리한다. 미확정 설계에 빈 V1을 요구하지 않는다.
- 적용 이력을 보지 못했다면 기존 파일이 이미 적용되었다고 단정하지 말고 확인을 요청한다.

## 9. ENUM

**검토·판단 기준**

- 정해진 상태·역할·유형에 사용하며 타입은 PascalCase, 상수는 UPPER_SNAKE_CASE인지 확인한다.
- 영속 필드가 @Enumerated(EnumType.STRING)을 사용하고 ORDINAL을 사용하지 않는지 확인한다.
- DB 컬럼은 기본 VARCHAR이며 실제 ORM 매핑과 SQL의 타입·길이가 일치하는지 확인한다. MySQL/Hibernate에서는 @JdbcTypeCode(SqlTypes.VARCHAR) 같은 명시적 매핑을 확인한다.
- 상수 추가 시 관련 분기가 누락되지 않았는지, 이름 변경·삭제 시 기존 DB 값과 API 소비자에 대한 영향을 검토했는지 확인한다.
- 데이터 변경이 필요하면 Flyway 마이그레이션이 있는지 확인한다.
- 도메인 전용은 해당 도메인.enums, 실제 공유 타입만 global.enums에 배치하는지 확인한다.

**허용 예외**

- ErrorCode와 SuccessCode는 global.response.code에 함께 둔다.
- 이름 변경·삭제 자체를 무조건 금지하지 않는다. 영향 검토와 필요한 데이터 전환이 준비됐는지 판단한다.

## 10. 암호화 및 민감정보

### 10.1. 저장 대상과 방식

- 데이터의 저장 필요성·민감도·조회 목적에 따라 암호화 여부를 결정했는지 확인한다.
- 복원이 필요한 민감정보는 AES-256-GCM, 비밀번호는 BCrypt·Argon2 같은 단방향 비밀번호 해시를 사용하는지 확인한다.
- 외부 호출에 다시 쓸 인증 토큰은 복호화 가능한 형태로 보호하는지 확인한다. 검증만 필요한 토큰은 단방향 해시를 우선 검토한다.
- 불필요한 개인정보를 저장하거나 평문 복사본을 별도 컬럼에 남기는지 확인한다.
- 개인정보라는 이유만으로 모든 필드의 암호화를 강제하지 않는다. 이름·이메일·전화번호 및 조회용 소셜 ID는 사용 목적에 따른 결정을 확인한다.

### 10.2. 암호화 구현

- 공통 암호화 서비스, JPA 암호화 Converter, 암호화 예외는 global.crypto에 함께 배치한다. 키 설정 클래스는 global.config에서 관리한다.

- 공통 EncryptionService에 알고리즘 처리가 모여 있고 도메인별 중복 구현이 없는지 확인한다.
- AES-256-GCM의 32바이트 키, 12바이트 IV, 16바이트 인증 태그를 사용하는지 확인한다.
- 매 암호화마다 SecureRandom으로 새 IV를 생성하고 같은 키에서 재사용하지 않는지 확인한다.
- 고정 IV·하드코딩 키, 인증 태그 검증 누락, 변조 오류 무시를 확인한다.
- 저장 형식에 버전 정보, IV, 암호문과 인증 태그가 포함되고 키 교체 시 기존 데이터 복호화를 고려했는지 확인한다.
- Base64는 저장용 인코딩이다. 암호화 대신 인코딩만 사용하는지 확인한다.

### 10.3. JPA 변환

- EncryptionConverter가 AttributeConverter를 구현하고 알고리즘은 EncryptionService에 위임하는지 확인한다.
- @Converter(autoApply = false)와 필드의 명시적 @Convert로 대상이 제한되는지 확인한다.
- null을 그대로 처리하며 Service가 중복 암호화·복호화를 수행하지 않는지 확인한다.
- Native Query·JDBC 등 Converter를 우회하는 접근에서 자동 암호화를 가정하지 않는지 확인한다.
- Converter는 엔티티 로딩 시 복호화할 수 있다. 필요한 데이터만 조회하고 접근 권한을 확인하는 실제 흐름을 검토한다.

### 10.4. 키 관리

- 키가 소스·DB에 직접 저장되거나 키가 담긴 .env·설정 파일이 커밋되는지 확인한다.
- 로컬·테스트·운영의 키가 분리되고 외부에서 주입되는지 확인한다.
- 키 누락·잘못된 길이 등에 대해 시작 단계에서 실패하도록 처리하는지 확인한다.
- 키 버전, 기존 키로의 복호화, 재암호화 정책 및 키 접근 권한을 고려했는지 확인한다.
- 초기 환경의 환경변수 주입을 허용한다. 운영의 KMS·Secrets Manager는 우선 검토 대상이며 특정 서비스를 강제하지 않는다.
- 백업이나 운영 권한처럼 코드로 알 수 없는 상태는 확인 필요로 남긴다.

### 10.5. 검색과 DB 변경

- 무작위 IV를 사용하는 암호화 컬럼에 평문처럼 동등 비교·LIKE·중복 검사를 수행하는지 확인한다.
- 검색이 필요하다면 HMAC 기반 Blind Index 등 합의된 방식을 사용하고 검색용 키가 암호화 키와 분리되는지 확인한다.
- 검색을 위해 원문을 별도 저장하는 우회가 없는지 확인한다.
- 컬럼 용량이 원문의 최대 바이트 길이, IV·태그·버전 정보, 인코딩 증가분을 수용하는지 확인한다.
- 암호화 컬럼 추가·타입 변경은 Flyway로 관리하고, 기존 평문 전환에는 데이터 마이그레이션 절차가 있는지 확인한다.
- 저장량에 맞는 TEXT·VARBINARY 등의 선택은 허용한다.

### 10.6. 실패 처리와 정보 노출

- 암호화 실패 시 평문을 저장하거나, 복호화 실패 시 기본값·암호문으로 대체하는지 확인한다.
- 암호화·복호화 오류를 별도 예외로 처리하는지 확인한다.
- 키·개인정보 원문·인증 토큰이 로그, 예외 메시지, API 응답에 노출되는지 확인한다.
- 오류 로그에는 민감정보를 제외한 오류 유형과 추적 식별자만 남기는지 확인한다.
- 복호화된 API 응답은 사용자 권한을 확인하고 필요한 정보만 반환하는지 확인한다.

### 10.7. 테스트 존재 및 범위

암호화 기능이 변경된 경우 공통 컴포넌트 단위 테스트와 JPA 통합 테스트가 다음을 다루는지 확인한다.

- 암호화·복호화 왕복 시 원본 일치
- 동일 원문 반복 암호화 시 다른 암호문 생성
- 암호문 변조 시 복호화 실패
- null 처리
- JPA 저장·조회 시 자동 변환
- 실제 저장 데이터가 컬럼 길이를 초과하지 않음

테스트 작성 여부와 실제 실행 결과를 구분한다. 리뷰만 요청받았다면 임의로 테스트를 실행하지 않고 확인한 범위만 보고한다.
